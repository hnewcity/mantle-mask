# 用量报表性能（v0.3.1）

## 瓶颈与修复

`GET /api/admin/usage?all=true` 以及个人用量接口原先先扫描模型 / 上游组合，再分别计算总计、用户、密钥、模型、上游、日期、日期 × 模型。每个维度重复扫描历史请求，并重复通过 `json_each` / `json_extract` 关联价格及计算长上下文费用；刚配置单价后尤其明显。

v0.3.1 用一个参数化查询流式读取同一 SQLite WAL 快照，对每次请求只计算一次费用，同时累加所有维度。当前请求内缓存模型 / 上游价格解析和日期格式化结果，缓存不会跨报表请求保留；没有缓存历史金额或把全部请求加载为 Go 切片。读取完成即释放数据库快照，输出分组仍按原顺序排序。

- 保留服务端用户权限范围和日期、用户、Key、上游、模型过滤；不在 Go 侧读取其他用户后再过滤。
- 缓存 Token 仍从普通输入扣除，推理 Token 不重复收费；长上下文阈值仍按单次请求的完整输入判断。
- 价格覆盖、上游区域 / 别名修改、用量补齐、备份恢复会在下一次查询立即生效。
- 未定价、零单价、未返回用量、进行中及待补齐继续区分。
- 保留旧 SQL 的名称选择与时区语义；整数溢出返回错误，不返回负数统计。
- API JSON 字段和 SQLite schema 均不变，升级无需迁移数据库。

## 可复现验证

```bash
go test ./internal/usage -run 'TestSinglePassReportMatchesLegacy|TestReportCancellationReleasesReader|TestReportRejectsTokenOverflow'
go test ./internal/usage -run '^$' -bench '^BenchmarkUsageReport$' -benchtime=1x -count=3 -benchmem
```

`report_legacy_test.go` 只在测试中保留 v0.3.0 的 SQL 实现，作为输出一致性的独立基准；它不进入生产二进制。合成数据覆盖 4 类模型、多用户 / Key / 上游、区域参考价、手动覆盖、免费和未知价格、272K 边界、缓存大于输入、失败及进行中请求、待补齐状态、重命名实体、空库和正负时区。测试逐字段核对总计与全部分组；金额只允许浮点累加顺序导致的舍入差异。

基准测试只使用临时数据库和合成数据，不读取生产数据库、不调用真实模型。它测量存储层生成完整报表的耗时，不包含网络传输、服务器硬件差异或浏览器渲染。流式行读取会增加一些 Go 临时分配，但不保留全部历史记录；内存中的汇总结构大小取决于不同分组的数量。

## 本地测量（2026-10-16）

环境：WSL2 / Linux amd64，Go 1.27.2，AMD Ryzen 5 3450U（Go 可见 2 个 CPU），临时 SQLite WAL 数据库。相同夹具、同一进程中分别运行新旧实现，2 万条请求各测 3 次：

| 实现 | 第 1 次 | 第 2 次 | 第 3 次 | 中位数 |
| --- | ---: | ---: | ---: | ---: |
| v0.3.0 重复 SQL 聚合 | 6,613 ms | 6,354 ms | 6,376 ms | 6,376 ms |
| v0.3.1 单次流式聚合 | 96 ms | 97 ms | 97 ms | 97 ms |

这一组合下中位耗时降低约 98.5%，约快 65 倍。10 万条夹具也运行通过；由于该轮同时执行前端安装 / 构建，存在明显资源竞争，不将其耗时作为对外性能承诺。上述结果是本机合成数据微基准，不是生产服务器的响应时间 SLA。
